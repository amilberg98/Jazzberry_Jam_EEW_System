# EEW Algorithm Testing Framework

This repository contains the **software testing infrastructure** for the Earthquake Early Warning (EEW) system developed at Tufts University in partnership with Schneider Electric. The goal of the larger project is to build a portable, affordable EEW device (under $90) capable of detecting seismic P-waves and issuing alerts with under 3 seconds of latency — without requiring internet connectivity.

This repo focuses specifically on **validating the earthquake detection algorithms** (STA/LTA, τc, Pd) against real-world seismograph data before those algorithms are deployed to the embedded hardware.

```

```


## Test Framework: Catch2

This project uses **Catch2 v3** as its testing framework (vendored as a single-file amalgamation). Catch2 is a header-only-style C++ test framework that uses macros to define test cases and assertions without requiring you to register tests manually.

### How the Test Runner Is Bootstrapped

`tests/main.cpp` defines the Catch2 entry point:

```cpp
#define CATCH_CONFIG_MAIN
#include "catch_amalgamated.hpp"
```

`CATCH_CONFIG_MAIN` tells Catch2 to generate the `main()` function automatically. This means **you must not define `main()` yourself** in any other test file. All test files are compiled and linked into the single `tests_runner` binary.

### Custom Output Listener

`main.cpp` also registers a custom event listener called `DefaultOutputListener`:

```cpp
class DefaultOutputListener : public Catch::EventListenerBase {
    void testCaseStarting(...) { /* prints === Test Name (tags) === */ }
    void testCaseEnded(...)    { /* prints assertion counts */         }
};
CATCH_REGISTER_LISTENER(DefaultOutputListener)
```

This listener hooks into Catch2's event system to print a formatted header before each test case and a summary of passed/failed assertions after it. You do not need to modify this to add new tests — it applies automatically to every `TEST_CASE`.

### Test Naming Convention

Test cases are named with a numeric prefix and use Catch2 tags for filtering:

```cpp
TEST_CASE("01_smcparser_metadata", "[smcparser]")
TEST_CASE("02_unit_test_sta_lta_over_multiple_smc_records", "[unit][stalta]")
```

- The **numeric prefix** (`01_`, `02_`, …) controls the display order in output and makes it easy to see which tests ran in sequence.
- **Tags** in brackets (e.g., `[smcparser]`, `[unit]`, `[stalta]`) allow selective test execution via `./tests_runner "[tag]"`.
- Follow this convention when adding new tests: increment the prefix and assign meaningful tags.

## Test Files

### smcparser_test.cpp

**Tag:** `[smcparser]`

Validates the `parseSmcFile()` function against a single known SMC file (`data/20021103_2212_uncorr/0528a_u.smc`).

**What it checks:**

- `rec.totalPoints` equals the actual number of values in `rec.dataPoints` — verifying the parser correctly counts samples.
- `rec.totalPoints > 0` — verifying the file was not empty or misread.

**What it prints** (for manual inspection):

- Station name, channel direction, start time, sampling interval
- Total number of data points
- The maximum absolute acceleration value in the record
- The first 5 data point values with their indices

This test is intentionally **informational as well as assertive** — the printed output lets a developer quickly spot-check that metadata fields are being parsed correctly even before writing assertions for every field.

---

### unit_test.cpp

**Tags:** `[unit][stalta]`

Runs the STA/LTA algorithm (once implemented) over a batch of 20 uncorrected SMC files from the `20021103_2212_uncorr/` dataset, covering stations `0528`, `0593`, `1356`, and `1397`.

**Current state:** The STA/LTA implementation in `src/algorithms/stalta.cpp` and `include/algorithms/stalta.hpp` is a stub. The test loads each file with `parseSmcFile()`, verifies the record is non-empty, and contains a placeholder `REQUIRE(true)` where the trigger verification logic will go.

**Intended full behavior (to be implemented):**

1. Seed the LTA using the first 2 seconds of data.
2. Begin the STA/LTA ratio calculation starting at t = 2s.
3. Detect trigger times where the ratio exceeds a threshold.
4. Assert that the detected trigger times match known expected values within a tolerance.

The `INFO("Processing file: " << path)` macro captures the file path in Catch2's failure context — if an assertion fails, Catch2 will print which file caused it, making batch failures easy to diagnose.

## The SMC Parser

The parser lives in `src/parsers/smcparser.cpp` and is declared in `include/parsers/smcparser.hpp`.

### AccelerometerRecord

```cpp
struct AccelerometerRecord {
    // Timing
    double samplingInterval;   // seconds per sample (e.g., 0.005 for 200 Hz)
    double sampleRateHz;       // samples per second
    int    totalPoints;        // number of samples in dataPoints

    // Event metadata
    std::string stationName;
    std::string channelDirection;  // e.g., "Up", "North", "East"
    std::string earthquakeName;
    std::string startTime;         // ISO-like: "2002-11-03T22:12:00"
    int eventYear, eventMonth, eventDay, eventHour, eventMinute;

    // Earthquake parameters
    double earthquakeLatitude, earthquakeLongitude, earthquakeDepthKm;
    double magnitudeM, magnitudeMs, magnitudeMl, magnitudeOther;

    // Station parameters
    double stationLatitude, stationLongitude, stationElevationM;
    double epicentralDistanceKm, epicentralAzimuthDeg;
    double vs30;  // shear-wave velocity of site (m/s)

    // Instrument parameters
    double naturalFrequencyHz, sensorDamping;
    double amplifierGainDb, preampGainDb;
    double antiAliasCornerHz, antiAliasPoles;

    // Time series
    std::vector<double> dataPoints;  // acceleration in cm/s²
};
```

### parseSmcFile()

```cpp
AccelerometerRecord parseSmcFile(const std::string& filePath);
```

Parses one `.smc` file from disk and returns a fully populated `AccelerometerRecord`. Throws `std::runtime_error` if the file cannot be opened or if the header is malformed.

**Parsing stages:**

1. **Text headers (lines 1–11):** Extracts earthquake name, event date/time, magnitude fields, station name, and channel direction using substring and keyword searches.
2. **Integer headers (6 lines, 48 values):** Read into a fixed-size array; fields are mapped to struct members by index per the COSMOS SMC specification.
3. **Real headers (10 lines, 50 values):** Same approach; includes sampling rate, coordinates, magnitudes, and instrument parameters. The sampling rate (`realHeaders[1]`) is mandatory — a missing or zero value throws an exception.
4. **Comment lines:** A variable number of free-text lines (count given by `headerNumComments` in the integer headers) are stored in `record.comments`.
5. **Data block:** All remaining whitespace-delimited floating-point values are parsed and stored in `dataPoints`. `totalPoints` is set to `dataPoints.size()` after parsing.

### SMC File Format Overview

COSMOS/SMC is a fixed-format seismological data format. A typical file has:

- 11 lines of free-text header
- 6 lines of integer parameters (8 values per line)
- 10 lines of real-valued parameters (5 values per line)
- Variable comment lines
- Data lines with acceleration values in cm/s²

## Test Data

### Data Directory Layout

```
data/
├── 20021103_2212_corr/    # Corrected recordings (baseline-corrected, instrument-response-removed)
└── 20021103_2212_uncorr/  # Uncorrected recordings (raw counts or minimally processed)
```

Both directories contain recordings from the **November 3, 2002 Denali Fault earthquake** (Mw 7.9), recorded at COSMOS strong-motion network stations. The directory name encodes the event: `20021103` = date, `2212` = origin time in UTC (22:12).

### File Naming Convention

Files are named using the pattern: `{station}{channel}_{type}.{ext}`

| Component   | Meaning                                                          | Examples                             |
| ----------- | ---------------------------------------------------------------- | ------------------------------------ |
| `{station}` | 4-digit station code (or alphanumeric for some networks)         | `0528`, `1356`, `k202`               |
| `{channel}` | Channel letter: `a` = first component, `b` = second, `c` = third | `a`, `b`, `c`                        |
| `_{type}`   | Processing level suffix                                          | `_u` (uncorrected), `_a`, `_d`, `_v` |
| `.{ext}`    | File format                                                      | `.smc` (COSMOS SMC), `.fs1`, `.rs2`  |

**Type suffixes in the corrected directory:**

| Suffix        | Meaning                    |
| ------------- | -------------------------- |
| `_a`          | Acceleration time series   |
| `_v`          | Velocity time series       |
| `_d`          | Displacement time series   |
| `_f` / `.fs1` | Fourier amplitude spectrum |
| `_r` / `.rs2` | Response spectrum          |

**Type suffixes in the uncorrected directory:**

| Suffix | Meaning                        |
| ------ | ------------------------------ |
| `_u`   | Uncorrected accelerogram (raw) |

Each station code represents a physical recording station. The three channel letters (`a`, `b`, `c`) correspond to the three axes of the triaxial accelerometer at that station (typically two horizontal components + one vertical).

### Corrected vs. Uncorrected Data

- **Uncorrected (`_uncorr/`, `_u.smc`):** Minimal processing — raw digitizer output converted to physical units. May include baseline drift, instrument response effects, and low-frequency noise. **These files are used by the current tests** because they most closely represent what an on-device accelerometer will produce.

- **Corrected (`_corr/`):** Full post-processing applied: baseline correction, instrument response removal, bandpass filtering. These are more accurate representations of true ground motion and are suitable for reference comparisons or magnitude calibration tests.

## Adding New Tests

### Adding a New Test Case

1. Create or open a `.cpp` file in `tests/`. Either add to an existing file or create a new one (e.g., `tests/tauc_test.cpp`).

2. Include the Catch2 header and any module headers you need:

    ```cpp
    #include "catch_amalgamated.hpp"
    #include "parsers/smcparser.hpp"
    #include "algorithms/stalta.hpp"
    ```

3. Write a test case following the naming convention:

    ```cpp
    TEST_CASE("03_tauc_basic_trigger", "[unit][tauc]") {
        AccelerometerRecord rec = parsers::parseSmcFile("data/20021103_2212_uncorr/0528a_u.smc");
        REQUIRE(rec.totalPoints > 0);

        // ... call your algorithm, then assert ...
        REQUIRE(someResult == Approx(expectedValue).margin(0.1));
    }
    ```

4. Add the new `.cpp` file to `TEST_SRC` in the `Makefile`:

    ```makefile
    TEST_SRC := tests/main.cpp tests/smcparser_test.cpp tests/unit_test.cpp tests/tauc_test.cpp
    ```

5. Run `make test` to rebuild and execute.

**Useful Catch2 macros:**

| Macro                                           | Purpose                                                 |
| ----------------------------------------------- | ------------------------------------------------------- |
| `REQUIRE(expr)`                                 | Assert and **stop the test** on failure                 |
| `CHECK(expr)`                                   | Assert but **continue** on failure                      |
| `REQUIRE(val == Approx(expected).margin(tol))`  | Floating-point comparison with absolute tolerance       |
| `REQUIRE(val == Approx(expected).epsilon(rel))` | Floating-point comparison with relative tolerance       |
| `INFO("msg")`                                   | Attach a message to the next assertion's failure output |
| `FAIL("msg")`                                   | Unconditionally fail with a message                     |

### Adding a New Algorithm Module

1. Create the header in `include/algorithms/yourmodule.hpp` and the implementation in `src/algorithms/yourmodule.cpp`.

2. Add the implementation source to `PARSER_SRC` in the `Makefile` (or add a new `*_SRC` variable):

    ```makefile
    ALGO_SRC := src/algorithms/stalta.cpp src/algorithms/yourmodule.cpp

    $(TEST_BIN): $(TEST_SRC) $(TEST_LIB) $(PARSER_SRC) $(ALGO_SRC)
        $(CXX) $(CXXFLAGS) $(TEST_LIB) $(PARSER_SRC) $(ALGO_SRC) $(TEST_SRC) -o $(TEST_BIN) $(LDFLAGS)
    ```

3. Write tests for the new module in `tests/`.

### Adding New Test Data

New `.smc` files should be placed in a subdirectory of `data/` following the existing naming convention. Name the directory after the event date and time: `data/YYYYMMDD_HHMM_corr/` or `data/YYYYMMDD_HHMM_uncorr/`.

Real COSMOS SMC datasets can be obtained from the [COSMOS Virtual Data Center](https://www.cosmos-eq.org/VDC.html) or the [CESMD Strong Motion Center](https://www.strongmotioncenter.org/).

## CI / GitHub Actions

The workflow file at `.github/workflows/ci.yml` automatically builds and runs the full test suite on every push and every pull request to any branch.

### What the workflow does

```yaml
on:
    push:
        branches: ["**"]
    pull_request:
        branches: ["**"]
```

| Step                | Description                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Checkout**        | Clones the repository including the `data/` directory, which the tests read at runtime                                                            |
| **Install clang++** | Installs `clang` via `apt-get` on the Ubuntu runner, matching the compiler specified in the `Makefile`                                            |
| **Build**           | Runs `make`, which compiles `lib/catch_amalgamated.cpp`, `src/parsers/smcparser.cpp`, and all files under `tests/` into the `tests_runner` binary |
| **Run tests**       | Runs `make test`, which executes `./tests_runner` and exits with a non-zero code if any `REQUIRE` assertion fails — causing the workflow to fail  |

### Viewing results

Go to the **Actions** tab of the GitHub repository to see per-run logs. Each step's output is captured, so a failed `REQUIRE` will show the full Catch2 failure message (including any `INFO(...)` context) directly in the CI log.

### Adding a new job

To add a parallel job — for example, a noise test or a performance benchmark — add another entry under `jobs:` in `ci.yml`:

```yaml
jobs:
    test:
        # ... existing job ...

    noise-test:
        name: Noise / False-Trigger Tests
        runs-on: ubuntu-latest
        steps:
            - uses: actions/checkout@v4
            - name: Install clang++
              run: sudo apt-get update -y && sudo apt-get install -y clang
            - name: Build
              run: make
            - name: Run noise tests
              run: ./tests_runner "[noise]"
```

The `./tests_runner "[noise]"` invocation uses Catch2's tag filter so only tests tagged `[noise]` run in that job.
